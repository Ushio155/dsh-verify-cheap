# 反模式与事故记录（anti-patterns）

配合 `SKILL.md` 使用。以下条目来自实际验证过程中的失败案例：结论与具体技术栈无关，命令样例保留原始形态以便对照复现。文中路径均相对本技能目录（`skills/verify-cheap/`）。

## 1. 用重型套件回答轻量问题

| 反模式 | 问题 | 替代做法 |
|---|---|---|
| 为一行样式规则文本跑整轮端到端测试 | 成本从 <1 s 升到数分钟；失败信息被大量无关输出淹没 | 改为 L0 静态断言（规则值 / 文本比对） |
| 为了拿一个数字重跑整轮测试 | 同一个数字，探针 5–15 s 即可取得 | 抽成可复用探针，见 `probe-cookbook.md` |
| 把"最小验证集"当作跳过发版前 L3 的理由 | 降档只适用于小改动 | 发版门禁执行完整 L3，一项不减 |

## 2. 用固定延时等待（原始写法）

```
Start-Sleep 240              # 等后台作业
Start-Sleep -Seconds 280     # 换写法不改变性质
```

```
while (!done) await sleep(2000);   // 无超时轮询
await sleep(8000);                 // 脚本内固定延时
```

- 问题：条件可能 5 s 即满足（白等），也可能 300 s 仍未满足（假红），固定值无法同时覆盖两种情况。
- 替代：启动后台作业后结束本轮，用 `job_output(wait: true)` 取结果；脚本内部用条件轮询 + 超时，见 `scripts/wait-until.mjs`。
- 已发生的后果：一个 59 s 完成的作业被记为"5 分钟"，该数字随后写进注释与汇报。
- **合法例外**（三个条件必须同时满足，缺一即为猜）：① 先等**触发条件**满足；② 延时基于**已知**时序，"工具每 100 ms tick，要 2 个 tick ⇒ 200 ms"这类可推算的值；③ 注释写清理由。写法固定为"先等条件，再等已知时长"。
- 手写轮询时的两个坑：**间隔别太密** —— `setTimeout(check, 1)` 是空转烧 CPU，从 10 ms 起（`wait-until.mjs` 默认 500 ms）；**取值必须写在循环内** —— 循环外取一次拿到的是旧值，条件永不更新，等价于固定延时。

## 3. 把逻辑塞进一次性内联命令

```
node -e "console.log(require('fs').readFileSync('out.json').length)"
```

- 问题：引号转义在 PowerShell 下容易出错；逻辑无法复用；取一次值即丢弃。
- 替代：把片段落地成文件后运行，或复用现成探针外壳。确需一次性求值时保持单行、不嵌套引号。

## 4. 恒真断言

实例：用 `offsetWidth - clientWidth <= 8` 判断滚动条宽度。无头 Chromium 使用 overlay scrollbar，该差值恒为 0，断言永远通过。

- 替代：读取实际属性并断言具体值，例如 `getComputedStyle(el, '::-webkit-scrollbar').width`。
- 通用检查：断言中避免"存在 / 不为空 / 小于某个数"这类弱条件；每条断言都应能举出使其失败的具体场景。

## 5. 进程未退出导致外部耗时虚高

反模式：验证脚本成功后未调用 `process.exit()`，Node 继续等待事件循环排空（未关闭的句柄 / 连接 / 定时器），外部耗时远大于脚本内计时。

- 判据：`外部总时长 − 脚本内计时` 超过数秒即视为异常（阈值定义见 `cost-measurement.md`）。
- 替代：成功路径同样显式 `process.exit(0)`；或统一用 `scripts/measure-runtime.mjs` 测量外部耗时并读取提示。
- 注意：`process.exit()` 会丢弃未 flush 的输出与未完成的写入，退出前应完成必要落盘。

## 6. 用印象代替测量

- 反模式：用"大概 / 感觉 / 印象里"回答"为什么这次这么慢"。
- 替代：引用项目成本表中的实测值（命令 + 档位 + 耗时），记录格式见 `cost-measurement.md`。
