# 用最低成本验证改动（verify-cheap）

目标：为每个改动选**能给出确定结论的最便宜手段**，让等待、耗时、断言都基于条件判断与实测，而不是固定延时与印象。

## 一、成本阶梯（L0–L3）

| 档 | 手段 | 参考耗时 | 适用场景 |
|---|---|---|---|
| L0 静态 | 读代码、语法检查、规则文本断言、编码检查、文本搜索 | <1 s | 只改文本 / 样式规则值 / 常量 / 字符串 / 注释 |
| L1 探针 | 单页运行时探针、一次性表达式求值、REPL：只回答"当前这个值是多少" | 5–15 s | 需要真实运行时的某个数值 / 样式 / 状态 |
| L2 集成 | 一个测试脚本或一个子套件 | 30–90 s | 改动涉及注入、落盘、生成、事件、跨模块行为 |
| L3 全量 | 完整测试套件、构建 + 校验、发版检查 | 数分钟 | 发版前，或改动触及公共代码 / 构建 |

耗时列只用于**初判档位**，是本机经验值而非承诺。落档与汇报一律以成本表里的实测值为准（第五节）。

## 二、怎么选

判据：**这次改动改变的是"行为"，还是只改变"表现 / 文本"？**

1. 只改文本 → L0，不启动运行时。无法确定 → 先用 L1 取事实，再决定是否升档。**不要用 L3 回答 L1 的问题。**
2. 要现场事实时只写**一个片段**，复用现有探针外壳，不要新建整套脚本。**探针外壳**指一个能加载目标运行环境、只暴露一次求值入口的最小脚本，应当具备的能力清单见 `references/probe-cookbook.md` 第四节。
3. 只有 L2 / L3 才算"回归验证"；跑完把结论与实测耗时写入报告。
4. 收尾自问：这次验证有没有更便宜的等价手段？有就固化进测试套件或成本表（第五节），下次直接复用。
5. **把坑沉淀给下一个会话**：这次验证挖出的**读代码读不出来**的事实（某个命令必须带什么参数、哪个环境限制会咬人、哪个"无害"改动曾经炸过）要落进该仓库的长期索引（`SUMMARY.md` 一类）。README 只放"怎么跑"；这类"为什么这么跑 / 什么坑不能踩"只写进 README 或阶段笔记，源码变动时不会有任何东西报警。

**直接跳档 / 不适用**：

- 改动触及公共代码、构建配置或依赖版本 → 直接 L3，不必先走 L0 试探。
- 探索性调试（还不知道要验证什么）→ 先弄清问题再选档，此阶段不存在"最便宜手段"。
- 安全、并发、时序类改动 → 静态检查的置信度极低，直接从 L2 起步。

## 三、等待后台作业

1. 启动后台作业后**立即结束本轮**，运行时会主动通知结果；需要时用 `job_output(wait: true)` 一次到位。**不要用固定延时（`sleep` / `Start-Sleep` 之类）等待后台作业。** 当前运行时若没有作业通知或等待工具，改用 `scripts/wait-until.mjs` 条件轮询。
2. 固定延时两头都不对：条件早满足时要重试，晚满足就白等；它同时是分段计时里最大的不确定项。
3. 脚本内部的等待统一写成**条件轮询 + 超时**，直接调用 `scripts/wait-until.mjs`：

   ```
   node <skill-dir>/scripts/wait-until.mjs --timeout 120 -- <命令> [参数...]
   node <skill-dir>/scripts/wait-until.mjs --timeout 90 --file <产物路径>
   node <skill-dir>/scripts/wait-until.mjs --timeout 30 --port <端口>
   ```

   退出码就是结论：**0 = 条件已满足，1 = 超时，2 = 参数错误** —— 调用方按退出码区分，不必去解析日志文本。

4. **确实需要固定延时时，三个条件必须同时满足**：① 先等**触发条件**已满足；② 延时基于**已知**时序（"每 100 ms 一个 tick，要 2 个 tick ⇒ 200 ms"），不是估的；③ 注释写清理由。缺一即为猜 —— 等价反模式、例外写法与手写轮询的两个坑见 `references/anti-patterns.md` 第 2 条。

## 四、断言必须能失败

- 写断言前先问：**这条断言在什么情况下会失败？** 举不出场景即为恒真断言，等价于没有验证。
- 优先断言**具体取值 / 具体类名**，而不是"存在 / 不为空 / 小于某个数"。实例与识别方法见 `references/anti-patterns.md`。

## 五、耗时必须实测

- 脚本自行打印**分段耗时表**（按 `[小节]` 边界），并同时输出**外部总时长 vs 脚本内计时** —— 两者差距明显说明有句柄 / 连接 / 定时器挂在事件循环上，修法是成功路径显式 `process.exit(0)`（见 `references/anti-patterns.md` 第 5 条）。
- 汇报耗时给出实测值与出处（哪个脚本、哪一段），不说"大概 / 感觉 / 印象里"。
- 每次验证记录三项：**档位、实测耗时、能否再降一档**；项目内维护一张成本表，落在仓库根 **`.verify-cost.md`** —— 仓库已有 `SUMMARY.md` 这类索引时就并进其中「成本表」小节，别再开第二份。汇报时直接引用而不是回忆。

  ```
  node <skill-dir>/scripts/measure-runtime.mjs --label "<档位 + 用途>" -- <命令> [参数...]
  ```

  计时实现、内外差异判定与成本表模板见 `references/cost-measurement.md`，可直接复用。

## 六、配套资源

`references/anti-patterns.md`、`references/probe-cookbook.md`、`references/cost-measurement.md`、`scripts/wait-until.mjs`、`scripts/measure-runtime.mjs`。

正文的判据不依赖这些文件：即使某个文件缺失或过时，成本阶梯、可失败断言、实测耗时三条仍然成立，照正文执行即可。
