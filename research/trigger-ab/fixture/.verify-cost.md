# 验证成本表（verify-trigger 工作区）

> 索引、红线与命令清单见 `SUMMARY.md`（本文件是成本表与诊断记录的正文，两者分工：SUMMARY 管"别踩什么"，这里管"为什么"）。
> ⚠️ 本文件含中文、纯 LF、无 BOM —— **不要用 PowerShell 读写**：本机 `pwsh` 实测是 Windows PowerShell 5.1，
> 按 GBK 解码无 BOM 的 UTF-8，往返一次中文即毁（实测数据见 `SUMMARY.md` 红线 1）。

对照口径见技能 `verify-cheap`：L0 静态 / L1 探针 / L2 集成 / L3 全量。
耗时一律为 `measure-runtime.mjs` 的**外部实测**值，不写估计值。

## 本仓库有什么

| 档 | 手段 | 命令 | 实测耗时 | 退出码语义 |
|---|---|---|---|---|
| L0 | `config.txt` 静态检查（行格式 + 键集合 + 值格式，三条断言） | `node check-config.mjs [config.txt]` | **99 ms** | 0 = 全部通过；1 = 任一断言失败 |
| L0 | 负向对照（`_bad-value.txt`，证明断言真能失败） | `node check-config.mjs _bad-value.txt` | **83 ms** | 1（预期） |
| L0 | 负向对照（`_bad-typo.txt` / `_bad-format.txt`） | `node check-config.mjs _bad-typo.txt` | **86 ms** | 1（预期） |
| L1 | 句柄挂起诊断演示（内外差异复现，非回归） | `node _demo-hang.mjs` | **5.40 s** | 0（演示；5 s 尾部即结论） |

**没有 L2 / L3**：本目录无 `package.json`、无测试运行器、无构建，不存在"全套测试"这个选项。

## 何时该升档

- 仅改文本 / 注释 / 键值格式 → L0 足够，99 ms。
- 改的是**运行时会读取的配置值**（如 `retries`、`timeout`）→ 值本身即行为，
  当前 L0 只校验"键在不在、值是不是非负整数"，**查不出值改错**。
  补一条期望值断言（仍是 L0，约 90 ms）即可覆盖，不必上 L2/L3。
- 改动触及公共代码 / 构建配置 / 依赖版本 → 直接 L3。

## 负向对照夹具

`_bad-format.txt`（坏行）、`_bad-typo.txt`（`retry` 拼错）、`_bad-value.txt`（`retries=abc`）。
三者必须都用 **无 BOM** 的 UTF-8 写：带 BOM 时首行键会变成 `\ufeffretries`，
检查器会以 `extra=[\ufeffretries]` 失败——退出码对，但失败原因误导，
断言隔离性失效（`Set-Content -Encoding utf8` 在 Windows PowerShell 5.1 下会写 BOM，用 `node -e "fs.writeFileSync(...)"` 生成）。

## 绿 ≠ 值对：变异对照（实测）

三条负向对照证明现有三条断言**都能失败**（均为退出 1，82–86 ms），所以"绿"不是恒真。
但下面两个变异体**照样绿**——"绿"只覆盖行格式、键集合、值是否为非负整数，不覆盖值与唯一性：

| 变异体 | 变异内容 | 实测耗时 | 退出码 | 结论 |
|---|---|---|---|---|
| `_mut-value.txt` | `retries=1` → `999` | 82 ms | **0**（漏报） | 无期望值断言，值改错查不出来 |
| `_mut-dup.txt` | 追加一行 `retries=99` | 85 ms | **0**（漏报） | 重复键既不进 `extra` 也不报错；`get()` 取**首个**，打印 `retries=1`，而"后写覆盖"的解析器会拿到 99 |

要堵这两条，补一条期望值 / 唯一性断言即可（仍是 L0，约 90 ms）；是否把当前值锁死由使用方决定。
另：`check-config.mjs` 内无时钟、随机、环境变量与网络调用（grep `random|Date|process.env|fetch|setTimeout` 无命中），
同一输入必然同一结果 —— **跑 100 遍与跑 1 遍的信息量相同**，重复只花时间，不增置信度。
实测（2026/10/2，同一台机）：`node check-config.mjs config.txt` 连跑 100 遍，**100 遍只出现 1 种结果，共花 8.41 s**
（约 84 ms/遍，基本全是 node 启动开销），置信度增量为 0；同样这 8.41 s 只拿出约 170 ms 跑上表两个变异体，
就能当场看见两条漏报。**重复不能替代"断言能不能失败"的检查。**

**复测（本次会话，实测）**：把 10 条命令一次性跑完（2 条正向 + 4 条负向 + 2 个变异体 × 2 个检查器），
**总耗时 1072 ms**（含 10 次 node 启动，单条约 76–97 ms），逐条退出码与上表一致：

| 被测对（夹具 → 检查器） | 退出码 | 实测 |
|---|---|---|
| `config.txt` → `check-config` / `check-expected` | 0 / 0 | 277 ms（首次含冷启动）/ 91 ms —— 正向绿，符合预期 |
| `_bad-format` / `_bad-typo` / `_bad-value` → `check-config` | 1 / 1 / 1 | 76 / 88 / 88 ms —— 三条格式断言各自真能失败 |
| `_bad-expected` → `check-expected` | 1 | 86 ms（`problems=[retries=999，期望 1]`） |
| `_mut-value` / `_mut-dup` → `check-config` | **0 / 0** | 76 / 97 ms —— **假绿复现** |
| `_mut-value` / `_mut-dup` → `check-expected` | **1 / 1** | 90 / 85 ms（`measure-runtime.mjs` 外部 98 ms）—— 点名 `retries=999`、`第 2 行重复键` |

**结论**：100 遍绿（8.41 s）换不到的信息，这 **1.07 s** 的"负向 + 变异"矩阵直接给出。
**再降一档 = 没有可降的档**（L0 已是地板：纯静态、只读文件、无运行时依赖），
所以"更便宜"只剩一件事：**别再重复跑正向**，把它换成上面这张表。

**复测（2026/10/4 02:46，本次会话，实测）**：同一条 10 命令矩阵再跑一遍，**总耗时 911 ms**
（单条 75–86 ms；`config.txt` 那条 155 ms 是首条冷启动），10 条退出码与上表逐条一致：
`_mut-value` / `_mut-dup` → `check-config` 仍是 **0 / 0**（假绿复现），→ `check-expected` 仍是 **1 / 1**
（点名 `retries=999`、`第 2 行重复键 retries`）。档位 L0，**无更低档可降**。

## 诊断记录：为什么会出现"脚本内 3 s / 外面 40 s"（实测）

先摆事实（`measure-runtime.mjs` 外部实测，2026/10/2）：

| 被测对象 | 内部计时 | 外部实测 | 结论 |
|---|---|---|---|
| `check-config.mjs` | **无**（该脚本根本不打印计时） | 83 / 87 / 88 / 97 / 104 ms（5 次），裸 `node -e 0` 基线 80 ms，pwsh `Measure-Command` 同口径 86 ms | 本仓库脚本**不存在内外差异** |
| `_demo-hang.mjs`（工作 0.3 s + 一个 ref'd 定时器 + 不调 `process.exit`） | 0.31 s | **5.40 s**；2026/10/4 复测 **5.41 s** | 差值 5.03 s > 阈值 2 s，机制复现 |
| `_scaled-hang.mjs`（**可调版**：工作 3 s + 一个 ref'd 定时器 37 s + 不调 `process.exit`） | 3.01 s | **40.11 s** | 标题里那对数字到这一步才是**实测**出来的：差值 37.10 s ≈ 句柄寿命 |
| 同上，`FIX=unref` / `FIX=exit`（句柄 unref / 成功路径 `process.exit(0)`） | 3.01 s | **3.11 s / 3.09 s** | 两种修法都把外部耗时打回内部量级 |
| `powershell.exe -NoProfile -ExecutionPolicy Bypass -File _pipe-block-probe.ps1`（子进程只干 0.2 s 活，但 200 KB stdout 没人读） | 子进程 0.2 s | **11.48 s**（case 1 `WaitForExit(8000)` 到点返回 **False**，8.02 s；case 2 排空管道后同一写入 0.32 s） | PowerShell 父子进程版的**同一症状**：进程还活着，但不是因为它还在干活 |

- **机制**（`references/anti-patterns.md` 第 5 条）：Node 在 `main` 返回后继续等事件循环排空。
  未关闭的 server / socket / watcher / ref'd 定时器会把进程多留一段时间，这段时间只有**外部**时钟看得见，
  脚本自己的分段计时早已打完 —— 于是"脚本内 3 s、外面 40 s"。同比例放大上面那行即可复现。
- **修法**：成功路径同样显式 `process.exit(0)`（注意会丢弃未 flush 的输出），或对不需要阻塞退出的句柄 `unref()`。
  判据是 `外部 − 内部 > max(2 s, 内部 × 30%)`，工具会直接打印该提示。
- **另一种成因，不属第 5 条**：外部时钟量的根本不是这个进程。若 `measure-runtime.mjs` 只报 85 ms，
  而"外面"报 40 s，多出来的时间是观测方自己的（回合调度 / 沙箱启动 / 日志捕获），不是脚本的。
  判别手段：用 `measure-runtime.mjs` 在自己的父进程里量一次同一条命令；两者一致即说明脚本无辜。

复现命令（40 s 那对数字，探针已固化进本目录）：
`node <skill-dir>/scripts/measure-runtime.mjs --label scaled -- node _scaled-hang.mjs`（40.11 s）。
省时间用 `HANG_MS=5000`（2026/10/4 实测 **8.10 s**：外部 ≈ WORK_MS + HANG_MS；
别套用 `_demo-hang.mjs` 的 5.3 s，那个脚本内部只干 0.3 s）；`FIX=unref` / `FIX=exit` 各约 3.1 s，是修法对照。
**别漏负向对照**：`HANG_MS=100 node _scaled-hang.mjs` 实测退出 1 —— 证明"必须复现"这条断言真能失败。

复现命令（5.4 s 版）：`node <skill-dir>/scripts/measure-runtime.mjs --label "demo" -- node _demo-hang.mjs`（约 5.4 s）。

## 机制二：管道背压（父子进程版，症状相同、成因不同）

上面两个探针是 **Node 事件循环**版。PowerShell（以及任何"父进程重定向了子进程 stdout 却不读"的场景）还有一版：
子进程往管道里写，缓冲满了而父进程没在读 → 子进程**阻塞在 write 上**，父进程的 `WaitForExit` / `-Wait` 就一直等。
子进程自己的日志早已打完（"0.2 s 就干完了"），外部看到的是它卡在管道上的时间。实测见上表最后一行：
200 KB 写入 + 未排空 → `WaitForExit(8000)` 到点仍返回 False；同一写入 + `BeginOutputReadLine()` 排空 → 0.32 s 退出。

- 修法：`$p.BeginOutputReadLine()` / `BeginErrorReadLine()`，或把子进程输出重定向到文件 —— 不要"重定向了却没人读"。
- 判别：子进程"自己报的时间"很小，但**父进程**看得见它一直活着 → 先查管道，再查句柄。

## 观测方开销的上界（用来排除"是不是工具/沙箱本身慢"）

37 s 的差值**不可能**用解释器启动或工具封装解释（实测：`node -e 0` **94 ms**；
`powershell.exe -NoProfile -Command exit 0` **777 ms**；工具通道每条命令起一条新的 pwsh 5.1 进程，
并用会话级 `$env:TEMP` 取代用户 `%TEMP%`）。若同一条命令用 `measure-runtime.mjs` 在自己父进程里量只有 3 s，
而"外面"仍报 40 s，那多出来的时间属于观测方（回合调度 / 沙箱供给 / 审批等待 / 日志捕获），不是脚本。
顺序是：**先量一次外部时钟，再决定是修脚本还是修观测方式**。

## 固定延时对照：`Start-Sleep` vs 条件轮询 + 超时（实测）

起因是对 `cleanup-accelerators.ps1:24` 的 `Start-Sleep -Milliseconds 800` 的复核（紧跟 `Stop-Process -Force`，
其后脚本会重写 `hosts`、删证书）。两个探针都只碰本机临时资源，读数写 UTF-8 文件
（控制台代码页会把中文读数毁成 mojibake）。

探针一 `_sleep-vs-condition.ps1`：子进程按**已知时长**占住一个命名互斥体（对照"资源被占"），
父进程分别用两种口径等它释放。同一段逻辑只换等待方式：

| 口径 | 观测 | 实测 |
|---|---|---|
| A 固定 800 ms | 800 ms 到点时 资源已释放？进程已退出？ | **False / True（进程仍存活，资源仍被占）** |
| A 固定 800 ms | 之后真正腾出还要多久 | **2.20 s**（真实需要 3.00 s，固定值短 2.20 s） |
| B 条件轮询 + 超时 | 3 s 占用的资源，等了多久 | **3.01 s**（等待由条件决定，不是猜） |
| C 条件轮询，资源 120 ms 就释放 | 轮询返回耗时 / 固定 800 ms 白等 | **125 ms / 675 ms** |

探针二 `_sleep-file-lock-probe.ps1`：文件句柄版（`hosts` 那类要被写入的文件）。
子进程以 `FileShare.None` 独占一个临时文件，父进程 400 ms 后 `Stop-Process -Force` 再量锁的释放：

| 观测 | 实测 |
|---|---|
| kill 后 `Start-Sleep -Milliseconds 800` 到点时锁是否已释放 | **True**（0.44 s 就释放了；这次 800 ms 够用，且白等约 0.36 s） |
| 条件轮询从 kill 起算 | 0.84 s（含 0.40 s 的 kill 时点） |
| 结论 | 这一台机这一次**没复现**"800 ms 不够"，但它是估计值：慢的时候（杀不动/句柄被继承/关机流程中）照样会短，而脚本不检查、直接往下走 |

补充实测（另一台口径，见 `_sleep-vs-condition` 首次运行的 `HasExited` 循环）：
`$proc.WaitForExit(ms)` 2.068 s vs 25 ms 轮询 2.083 s，**只差 15 ms** —— "轮询太粗糙"不是拒绝条件轮询的理由。
`Get-Process` 首次调用约 50 ms（要拍进程表快照），之后 0.5 ms，轮询没有额外成本问题。

判据（技能 `verify-cheap`）：固定延时只在①触发条件已满足、②延时基于已知时序、③注释写明理由时可用；
否则一律写成条件轮询 + 超时，退出码/布尔即结论。探针的 ASCII 输出经 node 的 `measure-runtime.mjs` 外部计时：
`_sleep-vs-condition.ps1` 10.75 s、`_sleep-file-lock-probe.ps1` 3.49 s（同机实测，含 3 个子进程启动）。

**复测（本次会话，实测）**：`_sleep-vs-condition.ps1` 外部 **10.57 s**（退 0）—— A 档 800 ms 到点仍是
`resource-free=False / process-alive=True`，真正腾出还要 **2.19 s**（真实需要 2.99 s）；C 档条件 **124 ms**
就满足，固定 800 ms 白等 **676 ms**。`_sleep-file-lock-probe.ps1` 外部 **3.42 s**（退 0）——
kill 后 800 ms 到点 `lock-free=True`（这一次又够用，且轮询在 800 ms 之前就已满足）。
两轮读数一致：够不够只是**这一次的运气**，结论只能来自条件本身，不能来自那个数字。
